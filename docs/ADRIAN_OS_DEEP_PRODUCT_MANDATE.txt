1. PURPOSE OF THIS ADDITIONAL MANDATE

You have already received the existing Adrian OS blueprints, Kimi Code integration blueprint, repository audit instructions, implementation instructions, personality specification, and previous execution prompts.

Those documents remain the existing project authority.

This document introduces an additional responsibility: independently evaluate the real product and identify what those previous documents, implementation passes, and current code have not adequately addressed.

Do not rewrite the earlier blueprints.

Do not create another competing architecture.

Do not repeat their entire feature lists as though those features are new requirements.

Do not simply tell the owner that the existing implementation is comprehensive.

Your job is to discover the difference between:

* What Adrian OS is intended to be.
* What the repository actually implements.
* What the production website actually serves.
* What an authenticated owner can actually use.
* What external integrations really execute.
* What is partially implemented.
* What is merely displayed in the interface.
* What is operational but unreliable.
* What is missing from the complete user experience.
* What should be improved to make the platform substantially more capable.

Then implement the appropriate improvements within the existing architecture.

The central objective is not to create more documentation. It is to improve the actual Adrian OS application.

The result must be a materially better, more coherent, more capable, more reliable and genuinely usable product.

4. THE BUILD MODULE MUST BECOME A COMPLETE, COHERENT WORKING ENVIRONMENT

The Build module is the most important product area in this mandate.

Do not treat it as a decorative chat window with a terminal panel.

It should become a coherent coding and project-execution workspace within Adrian OS.

The existing Kimi integration, Companion protocol, file operations, approval mechanisms and control plane must remain the foundation.

Improve that foundation rather than creating a second unrelated execution system.

4.1 Complete project workspace experience

Evaluate the complete project lifecycle.

A user should be able to:

* Create a project.
* Name a project.
* Select an approved workspace.
* Configure project instructions.
* Open an existing project.
* Resume work.
* View previous sessions.
* Rename sessions.
* Archive sessions.
* Recover sessions after refresh.
* Understand which project is active.
* Understand which runtime is executing the task.
* See whether the Companion is connected.
* See whether the selected provider is usable.
* Understand whether a task is queued, running, blocked, cancelled, failed or completed.

All project and session actions must operate on real persisted state.

Do not implement visual controls that merely change local UI state while leaving the actual project unchanged.

4.2 Improve the coding workspace

Evaluate whether the current editor is sufficient for real development work.

The existing bounded text editor should not be described as a full IDE.

Where technically appropriate, improve the editor experience with:

* A proper file explorer.
* Directory navigation.
* File search.
* File type recognition.
* Syntax highlighting.
* Line numbers.
* Search within the current file.
* Unsaved-change indicators.
* Save confirmation.
* Dirty-state protection.
* Diff visualization.
* File-change review.
* Revert and restore capabilities.
* Multiple open files.
* Tabs or another coherent multi-file navigation method.
* Large-file handling.

Consider Monaco or another appropriate editor implementation only after inspecting bundle size, browser compatibility, performance and actual integration requirements.

Do not install a large editor merely for visual prestige.

The final editor must be genuinely connected to the approved workspace.

4.3 File operations must be trustworthy

Audit every file operation.

Check:

* List.
* Read.
* Search.
* Create.
* Write.
* Rename.
* Delete.
* Restore.
* Diff.
* File-size limits.
* Path validation.
* Workspace root enforcement.
* Symlink handling.
* Concurrent modifications.
* Partial writes.
* Encoding.
* Binary-file handling.
* File locking.
* Operation cancellation.
* Error recovery.

Prevent path traversal, unintended deletion, writes outside approved roots and accidental corruption.

A successful write must be verified against the actual file.

A failed write must not be displayed as successful.

Where a write changes an existing file, preserve a recoverable before-state where practical.

4.4 Improve change review

A coding workspace should make changes understandable.

Provide a coherent review experience showing:

* Changed files.

4.5 Terminal and command execution

Requirements:

* Branch switching.

4.7 Task execution and progress visibility

Improve how the Build agent communicates progress.

The user should understand:

5. PROVIDER CONNECTIONS MUST BECOME REAL EXECUTABLE CONNECTIONS

The provider interface is a critical part of Adrian OS.

The current repository includes a Moonshot provider profile and encrypted key storage.

However, the current code explicitly identifies the stored provider’s runtime use as not_injected.

This is a significant product gap.

Do not confuse saving a credential with configuring a runtime.

5.1 Provider connection architecture

Audit every existing provider and its actual adapter.

Determine which providers can be used by:

* Adrian OS chat.
* Build.
* Kimi ACP.
* Background agents.
* EVE.
* Adrian Speak.
* Research.
* Other model-powered services.

Do not assume that a provider connected to one module is automatically available to every other module.

Implement an explicit provider-to-runtime mapping.

The owner should be able to choose the appropriate provider and model for the appropriate workload.

5.2 Provider management experience

Create or improve a clear provider connection experience with:

* Provider selection.
* API key entry.
* Base URL configuration where applicable.
* Model selection.
* Custom model support where valid.
* Connection testing.
* Model discovery where supported.
* Key validation.
* Credential status.
* Last successful test.
* Error diagnostics.
* Default model selection.
* Per-module routing.
* Provider fallback.
* Usage visibility.
* Disconnect and credential rotation.

Support the providers already present in the application’s architecture and any additional providers justified by real user needs.

Do not invent provider compatibility.

Use the provider’s actual API contract.

5.3 Kimi-specific connection behavior

Determine the exact execution mode.

If Kimi is running through its local CLI authentication, make that explicit.

If Kimi is using a configured API key, prove that the key is actually injected into the intended Kimi runtime.

If the provider profile is stored only for future use, show that clearly.

Do not leave a user believing that a saved key is powering Kimi when the runtime is still using another authentication method.

Test:

1. Credential submission.
2. Encrypted storage.
3. Server-side retrieval.
4. Runtime configuration.
5. Provider authentication.
6. Model selection.
7. Actual inference.
8. Failure handling.

5.4 Provider test results

A provider connection test must perform a real, minimal, controlled request when the provider supports it.

Return an honest result:

* Connected and verified.
* Credentials rejected.
* Model unavailable.
* Endpoint unreachable.
* Rate limited.
* Quota exhausted.
* Configuration invalid.
* Not tested.

19. CONTINUOUS VERIFICATION LOOP

The most important instruction in this document is that implementation must be followed by independent verification.

Do not stop when the code compiles.

Do not stop when the page renders.

Do not stop when the deployment succeeds.

For every substantial improvement:

1. Inspect the requirement.
2. Identify the relevant implementation.
3. Make the change.
4. Run the focused tests.
5. Run relevant regression tests.
6. Run typecheck.
7. Run lint where configured.
8. Run the production build.
9. Open the actual application.
10. Exercise the changed workflow.
11. Verify the backend result.
12. Verify persistence.
13. Verify security boundaries.
14. Record the evidence.
15. Correct failures.
16. Repeat the verification.

Independent review pass

After implementation, perform a second audit as though a different engineer had built the changes.

The reviewer must not rely solely on the implementation agent’s completion report.

Compare the actual code and behavior against the requirements.

Look for:

* Missing routes.
* Disconnected buttons.
* Incorrect API contracts.
* Incorrect state handling.
* Stale UI.
* Persistence gaps.
* Authentication gaps.
* Authorization gaps.
* Secret exposure.
* Race conditions.
* Broken cancellation.
* Inaccurate capability labels.
* Incorrect provider status.
* Mobile defects.
* Accessibility defects.
* Incomplete tests.
* Regression failures.

Fix confirmed defects.

Repeat the review until the defined acceptance criteria are met or a genuine external blocker remains.
