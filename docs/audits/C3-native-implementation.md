## Implemented behavior

**AA-066–071 — authenticated, recoverable updates.** One shared release contract validates signed versioned manifests, one to 64 ordered part files, source destinations, exact bytes/hashes, platform, timestamps and publisher pins before selecting a candidate. A malformed higher build cannot suppress a lower eligible build. Per-feed failures remain actionable. Download review gives exact bytes, part count and unpacked size; cache and installation volume checks happen before download. Completed verified parts and exact byte ranges can resume. An unsupported resume requires an explicit restart decision. A cached complete verified installer is reused. Installer signature verification is separate from metadata/hash verification, and a separate owner action is required to launch it. No timer silently downloads or launches a multi-gigabyte package.

`publisher-trust.json` intentionally contains no invented production public key or certificate. Current legacy build 9 remains unsigned and cannot authorize automatic installation. Release packaging forces code signing, requires a clean committed runtime identity, and the publish script refuses an unauthenticated manifest. Provisioning the reviewed publisher keys/certificate, producing a schema-v2 signed manifest and verifying Windows installation remain release tasks. These files do not change a published release or production trust state.

**AA-077–082 — explicit computer actions and truthful receipts.** A bounded typed plan replaces overlapping action regexes. Text payloads remain opaque, right/double clicks dispatch once, failed dependencies block subsequent effects, and current stop/permission checks run per step. Refusals and unsupported actions do not report `ran: true`. Discovery never invokes a matched button. A separate invocation names an exact window and re-resolves a unique target. Owner-folder reads/writes reject traversal and symlink crossing. Actual effects remain unverified unless a separate observation establishes them.

Screenshot interpretation requires an exact selected vision model and explicit external image permission. A fallback occurs only when explicitly named and authorized after a capability rejection. Provider receipts must identify the model actually used. Capture/provider/body waits share bounded cancellation; late callbacks do not dispatch a new model. A post-dispatch interruption is unknown and never automatically retried. The new Tools device panel separates paired presence from the current executor, supports explicit requests and screenshot review, displays receipt stages and capabilities, and requires device review before preparing another request after an uncertain result. Local PC result text is returned directly to chat instead of being silently added to an external model prompt.

**AA-160–166 — startup, recovery, lifecycle and platform truth.** The app-server compiles a build artifact ID and actual source revision; the launcher packages the same identity. The readiness endpoint verifies storage readiness and signs its exact compiled identity with a child-only secret and fresh challenge. Generic HTTP success, another process on the port, login pages and mismatched bundles do not establish readiness. `build:desktop-server` produces the node-server bundle, stages assets atomically and does not run migrations or the application. Generated artifacts remain outside Git.

Startup failures and child exits open a structured recovery window with retry, bounded redacted diagnostics, repair guidance and exit. The existing renderer remains intact so unsaved text can be copied. Manual restart is bounded. Closing the main window explicitly distinguishes hide/keep-running from exit; quitting cleans up the companion and owned child processes and bypasses the hide guard. NSIS allows directory selection; the custom full installer refuses an unrelated nonempty target and keeps user data separate from installation files. An old custom installation without the new marker needs an empty new target or a separately reviewed migration; it is not silently overwritten.

The capability matrix identifies Windows x64 as configured and physically unverified, other desktop targets as unsupported, and native iOS/Android apps as unimplemented. Source adapter availability is distinct from current engine, permission and action proof. The desktop Network menu exposes persistent local-only versus connected-services policy. Local-only blocks external renderer HTTP/WebSocket requests and server fetches, including redirect fallback. Explicit loopback Ollama requests remain possible if the local service is healthy. Local-only is an application transport policy, not an operating-system firewall for an explicitly requested shell command or an independently configured local-model server.

**AA-167 — shared core delivered; native mobile shells remain open.** The portable client contract binds operations to owner/workspace/base revision/idempotency ID, persists a dispatch claim, validates returned receipts, preserves original-account queue state after account changes and quarantines unknown outcomes instead of replaying them. The same synthetic operation runs through web, Windows and prospective mobile adapters. This is not a native iOS/Android application. Those platform containers and secure storage/media/lifecycle/notification adapters, signed builds and device acceptance are still required, explicitly recorded as blocked in the checklist.
