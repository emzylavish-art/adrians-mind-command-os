PART 1 — THE MISSION AND NON-NEGOTIABLE OBJECTIVE
1.1 The mission
Build a complete, production-quality Kimi Code experience inside Adrian OS.
The existing Adrian OS Build destination must become a powerful software-development environment in which the user can instruct an AI coding agent to inspect repositories, understand projects, plan tasks, create and modify files, execute commands, debug applications, work with Git, manage agents, use skills, manage integrations, run tests, review changes and carry out substantial software-development work.
The result must feel like a native Adrian OS product.
It must not be:
* A visual imitation of Kimi Code.
* A basic chat interface with a coding label.
* A page that simply redirects users to another product.
* A static dashboard with nonfunctional buttons.
* A frontend prototype disconnected from an execution engine.
* A collection of hardcoded responses.
* A mocked terminal that displays invented output.
* A feature catalogue that claims capabilities exist without implementing them.
* A system that only works in the developer’s local environment.
The goal is to connect the real Kimi Code engine to Adrian OS and expose its useful capabilities through Adrian’s own interface, authentication, projects, workspace management, security controls, integrations, voice experience and persistence infrastructure.
The user must be able to perform actual software-development work from the Adrian OS website.
1.2 What success looks like
A user signs into Adrian OS, opens Build, selects a project, chooses a model or provider, and instructs the agent to perform a substantial task.
The system should then be capable of:
1. Understanding the request.
2. Inspecting the existing project.
3. Reading relevant files.
4. Understanding the architecture and dependencies.
5. Creating an execution plan.
6. Identifying the files and systems that need to change.
7. Asking for approval when an action requires it.
8. Editing files.
9. Creating new files and directories.
10. Executing permitted terminal commands.
11. Installing permitted dependencies.
12. Running tests and builds.
13. Reading errors and diagnosing failures.
14. Revising its implementation.
15. Coordinating subagents when useful.
16. Tracking progress.
17. Showing file changes and diffs.
18. Reporting what was completed.
19. Preserving project and session history.
20. Resuming work after a browser refresh or temporary disconnection.
The experience must support meaningful multi-step engineering work, not merely question-and-answer interaction.
1.3 The website-first rule
The website is the first delivery target.
The initial implementation must operate through a persistent hosted execution environment. The user’s personal Windows computer must not be required for the website’s core Build functionality.
The architecture must support a future Windows Companion without making that companion a dependency for the first release.
The hosted runtime and Windows Companion must ultimately use the same Adrian Build interface and shared capability, authorization, event and policy contracts.
1.4 The ownership rule
Adrian OS remains the primary product and control plane.
Adrian OS owns:
* User identity.
* Authentication.
* Workspace ownership.
* Project authorization.
* Session ownership.
* Runtime assignment.
* Credential storage.
* Provider configuration.
* Integration governance.
* Approval policies.
* Usage and quotas.
* Audit records.
* Emergency stop.
* Device pairing.
* User preferences.
* Adrian Speak integration.
* User-facing experience.
Kimi Code supplies the coding-agent execution capabilities.
The integration must preserve a clear boundary between Adrian’s application responsibilities and Kimi’s execution responsibilities.
1.5 The no-fake-functionality rule
Every feature must be connected to a real operation.
A button must not appear functional when it is not connected to a working backend operation.
A status must not say connected when the connection has not been verified.
A task must not say completed when the runtime has not confirmed completion.
A terminal must not show fabricated output.
A plugin must not say installed merely because its name appears in a catalogue.
A session must not be considered saved merely because it remains visible in React state.
A test must not be marked passed merely because a mocked response was returned.
When a feature cannot work in the current environment, show its actual status and explain what is missing.
Use these status values consistently:
* VERIFIED
* PARTIAL
* BLOCKED
* UNSUPPORTED
* NOT_CONFIGURED
* NOT_AUDITED
* FAILED
* DISCONNECTED
Only mark a feature VERIFIED after its real end-to-end behavior has been demonstrated.

3.2 Application and runtime separation
The Adrian OS frontend and the Kimi runtime must be separate execution layers.
The frontend is responsible for user interaction.
The Adrian server is responsible for identity, authorization, routing, policy, persistence and governance.
The Kimi runtime is responsible for coding-agent execution.
The hosted runtime must not depend on a normal short-lived frontend request to stay alive.
Do not attempt to run a persistent Kimi process inside an ordinary Vercel serverless function.
Vercel can continue hosting the existing Adrian OS website and short-lived server operations. The persistent Kimi execution service must run on an appropriate persistent container, worker or virtual-machine environment.
3.3 Browser communication
The browser must communicate with Adrian OS server endpoints.
The browser must not:
* Receive Kimi runtime service tokens.
* Receive provider API keys.
* Receive private runtime addresses.
* Connect directly to an unrestricted runtime port.
* Control another user’s runtime.
* Bypass Adrian approval checks.
* Submit arbitrary filesystem paths without server-side validation.
The server authenticates the user, validates workspace access, checks policy, creates a task and forwards the permitted operation to the assigned runtime.
3.4 Runtime isolation
Every active workspace must have a defined isolation boundary.
Implement:
* Separate workspace filesystem roots.
* Separate runtime identities or equivalent tenant boundaries.
* Per-workspace process limits.
* Per-workspace storage limits.
* Per-task execution limits.
* Per-user concurrency limits.
* Restricted environment variables.
* Restricted network egress.
* Runtime lease expiration.
* Process cleanup.
* Workspace cleanup and retention rules.
* Isolation verification.
Never allow one user’s writable project directory, Kimi configuration, credentials, session data or process environment to become accessible to another user.
3.5 Runtime lifecycle
Implement a real runtime lifecycle:
1. User opens Build.
2. Adrian identifies the selected workspace.
3. Adrian checks whether an appropriate runtime is available.
4. The scheduler allocates or wakes the runtime.
5. The runtime verifies its identity.
6. The gateway checks runtime compatibility.
7. The runtime lease is created or renewed.
8. The project workspace is mounted or initialized.
9. The Kimi session is created or resumed.
10. The UI receives the runtime and session status.
11. Work is submitted.
12. The runtime executes.
13. Events are persisted and streamed.
14. The task finishes, fails or is canceled.
15. The runtime remains available or is suspended according to policy.
16. Session and project data remain recoverable.
3.6 Runtime recovery
The system must recover from:
* Runtime process crash.
* Runtime container restart.
* Network interruption.
* Browser refresh.
* WebSocket disconnection.
* Worker restart.
* Expired runtime lease.
* Failed task dispatch.
* Interrupted terminal process.
* Database temporary unavailability.
* Provider timeout.
* Kimi API incompatibility.
The system must distinguish between a completed task, a failed task, an interrupted task and an unknown task state.
Never automatically rerun a potentially destructive task simply because the browser reconnects.

PART 4 — KIMI CODE ENGINE INTEGRATION
4.1 Integrate the actual engine
Use the real Kimi Code engine.
The integration must preserve actual execution capabilities instead of implementing a separate simplified coding agent and presenting it as Kimi.
Inspect the upstream implementation and official documentation. Identify the exact release and supported runtime interface selected for Adrian Build.
The implementation team must verify:
* Kimi Code installation and startup.
* Supported runtime requirements.
* CLI execution.
* Server execution.
* REST API availability.
* WebSocket event availability.
* Session management.
* Agent execution.
* Tool execution.
* File operations.
* Terminal operations.
* MCP support.
* Plugin support.
* Skills support.
* Hooks support.
* Provider support.
* Subagent support.
* Configuration behavior.
* Supported attachment and media capabilities.
4.2 Use the actual runtime schemas
Where the selected Kimi runtime exposes OpenAPI and AsyncAPI documents, retrieve them from the exact pinned runtime.
Use those documents as the source of truth for the actual endpoints and events available in that version.
The integration must not assume that a route documented for a different version exists.
The adapter must:
* Store the schema snapshot.
* Record the runtime version.
* Record the schema digest.
* Validate required endpoints.
* Validate event structures.
* Detect incompatible runtime versions.
* Fail safely if mandatory operations are missing.
* Run contract tests during upgrades.
The documented Kimi server interfaces have included REST endpoints and WebSocket streaming, but the exact implementation must follow the selected runtime’s actual schemas.
4.3 Kimi runtime gateway
Create a dedicated server-side gateway that connects Adrian Build to the Kimi runtime.
Its responsibilities include:
* Runtime discovery.
* Runtime assignment.
* Authentication.
* Request forwarding.
* Request validation.
* Workspace binding.
* Session binding.
* Task dispatch.
* Event normalization.
* Cancellation.
* Timeout enforcement.
* Retry handling.
* Health checking.
* Compatibility checking.
* Error translation.
* Usage accounting.
* Audit recording.
The gateway must be the only normal application route into hosted Kimi execution.

9.4 Approval levels
Use an action-risk model.
Level 0 — Read-only
* Read permitted files.
* List files.
* Inspect Git status.
* Read session history.
* Inspect runtime health.
Level 1 — Ordinary project modification
* Create files.
* Edit files.
* Run ordinary project tests.
* Create project directories.
Level 2 — Elevated project action
* Install dependencies.
* Run scripts with broader effects.
* Change project configuration.
* Modify build settings.
* Execute commands with broader access.
Level 3 — Destructive or external action
* Delete substantial project data.
* Reset or overwrite work.
* Push to a remote repository.
* Change production deployment configuration.
* Remove important integrations.
* Perform actions with significant external consequences.
The exact approval behavior must be configurable by the owner.
An approval must identify the exact action and target.
A general approval must not become unlimited permission for unrelated future actions.
